# 01. AI 명령지침

이 명세를 읽고 풀림 게임즈를 구현하는 AI 에이전트가 따라야 하는 행동 규칙.

## 1. 사고 원칙

- **깊게 생각하라.** 코드 한 줄을 쓰기 전에 (1) 이 변경이 어떤 사용자 경험을 만드는가, (2) 어떤 명제를 검증하는가, (3) 실패 시 어떻게 보이는가를 먼저 답할 것.
- **스스로 검토하라.** PR 또는 커밋 단위로 본인이 만든 결과물을 다시 읽고, 명세와 어긋난 부분이 없는지 확인한 뒤 다음 작업으로 넘어갈 것.
- **사용자 의도를 파악하라.** 표면 요구가 아니라 그 뒤의 의도를 읽고, 의도와 어긋날 것 같으면 구현 전에 명세 작성자에게 확인할 것.

## 2. 명세 우선 원칙

- **명세가 source of truth.** 코드와 명세가 충돌하면 명세를 따르고, 명세 자체가 틀렸다고 판단되면 명세를 먼저 고친 뒤 코드를 고친다.
- **추론 금지.** 명세에 없는 결정을 임의로 채워 넣지 말 것. 모르면 묻고, 임시로 진행할 거면 명시적으로 표시(`TODO:`, `// SPEC-GAP:`)할 것.
- **연관 문서를 함께 본다.** 단일 파일만 보지 말고 관련된 다른 SPEC 문서, `proc/research/`, `~/.gstack/projects/pullim-games/`에 남은 의사결정 트레이스를 함께 참조한다.

## 3. 코드 작성 정책

- **새 파일/모듈 생성 전에 기존 자산 확인.** 신규 컴포넌트·모듈 작성 전에 `src/components/`·`src/lib/` 의 기존 자산을 grep 으로 확인하고, 재사용 가능한 helper·shell·primitive 가 있으면 그것을 활용한다 (4 메커니즘 컴포넌트 직접 활용 룰: `AGENTS.md` "4 메커니즘 컴포넌트" §).
- **Next.js 룰 — 본 리포 한정 분기.** 본 풀림 게임즈 리포의 Next.js 룰은 `proc/spec/09-기술-환경.md §9.1` 이 최종 권위 — **표준 Next.js 15.5+ (App Router)** 가 설치되어 있고 `node_modules/next/dist/docs/` 는 부재한다. 코드 작성 전에 `node_modules/next/dist/docs/` 를 먼저 읽으라는 지시 (다른 풀림 프로젝트의 AGENTS.md boilerplate) 는 본 리포 환경에서는 **적용 불가** — 표준 Next.js 컨벤션을 사용하고, 필요 시 공식 docs (nextjs.org) 를 직접 참조한다. 단, Next.js major upgrade·deprecation notice 가 보이면 진지하게 확인 (학습 데이터 컷오프 이후 breaking change 가능). 다른 풀림 프로젝트 (planner·Q·classbot) 의 Next.js 룰은 해당 리포의 docs·spec 을 따르며 본 분기 룰의 범위 밖. 본 분기 룰은 plan-g phase 1.7 (2026-05-26 G1 합의) 정합화 결과.
- **순수함수 우선.** AST 변환, FSRS 계산, 정답 판정 등 핵심 로직은 side effect 없는 순수함수로 분리한다. UI와 결합되면 테스트 불가.
- **Zod 스키마로 런타임 검증.** TypeScript 타입만 믿지 말고 외부 입력(카드 JSON, API 응답, 이벤트 페이로드)은 모두 Zod로 검증한다.
- **Boring tech 우선.** 검증된 라이브러리(`ts-fsrs`, `mathjs`, `Pretendard` 등)가 있으면 직접 구현하지 않는다. 단, 인터랙티브 수식 렌더링은 검증된 대안(MathLive 등) 평가 후 결정.

## 4. 테스트 정책

- **AST 변환 로직은 100% 단위 테스트.** Property-based test (`fast-check`)로 round-trip 검증.
- **Critical path는 E2E 테스트.** 첫 카드 진입, 5문제 시퀀스 완주, 7일 후 retrieval, 친구 링크 진입.
- **REGRESSION RULE.** 한 번 발견된 버그는 반드시 회귀 테스트를 추가한 뒤에 수정한다. 특히 fingerprint 손실로 인한 학습 데이터 단절은 silent failure이므로 테스트가 강제된다.
- **타겟 디바이스 매트릭스.** 갤럭시 A 시리즈, 아이폰 SE급에서 실 디바이스 검증을 하지 않은 채 머지 금지.

## 5. 배포 및 운영 정책

- **환경:** Next.js (App Router) + TypeScript + Vercel 배포. CI는 GitHub Actions.
- **PR 단위 Preview URL** 자동 생성. main 머지 = prod 배포.
- **번들 사이즈 게이트.** PR마다 `@next/bundle-analyzer` 결과를 코멘트하고, initial JS gzipped 300KB 초과 시 머지 차단.
- **익명 이벤트만 수집.** PII 0개. 만 14세 미만 처리는 V1에서 발생하지 않음(비로그인). 로그인 도입 시 정통망법 검토 재개.

## 6. 학습효과 우선 원칙 (Constraint #1)

- **중독 메커닉 금지.** 스트릭 압박, FOMO 푸시, 가챠, 무작위 보상 일정 등은 V1/V2에서 의도적으로 배제한다. 추가 검토 전에 함부로 도입하지 않는다.
- **외재 보상 최소화.** XP/레벨까지만. 그 이상의 보상 레이어 추가는 명세 작성자 동의 필요.
- **PVE 지향.** 또래 비교 메커닉(랭킹, 매칭, PvP)을 만들지 않는다. 본인 vs 본인 기록만 허용.
- **수능 점수 변환 증거가 베타 단일 KPI.** "MAU", "DAU"가 아니라 "학습 효과가 입증되는가"를 중심에 둔다.

## 7. 문서 위치 라우팅

사용자 요청을 받아 새 문서를 작성할 때 단계·성격에 따라 다음 위치에 둔다.

| 요청 표현 | 위치 | 단계 |
|---|---|---|
| "기획해줘", "기획문서 작성해줘", "플랜 만들어줘", "검토 문서" | `proc/plan/` | DRAFT (검토 대기) |
| "명세 작성해줘", "SPEC 작성해줘", "PRD" | `proc/spec/` | APPROVED |
| "리서치해줘", "조사해줘", "찾아봐줘" | `proc/research/` | 사실 자료 |
| "노하우 정리", "회고", "패턴 발견" | `proc/knowhow/` | 회고 |

**모호하면 `proc/plan/` 우선.** 기획 단계 문서는 DRAFT로 시작해서, 검토·승인 후 그 결정을 `proc/spec/` 에 반영하는 흐름이 표준이다.

⚠️ **트리거 충돌 주의:** `/create-spec` 스킬 설명에 "기획해줘"가 트리거 단어로 들어가 있지만, 이 프로젝트에서는 그렇게 처리하지 않는다. 명시적 "명세 작성", "SPEC 작성", "PRD 작성" 요청에만 `/create-spec` 을 호출하고, 일반 "기획해줘" 는 `proc/plan/` 에 기획서로 작성한다.

**파일명 규칙:** `proc/plan/` 안 파일은 `YYYY-MM-DD_<주제>.md` (예: `2026-05-08_parallel-game-architecture.md`). 같은 주제 재기획 시 새 날짜로 새 파일 생성, 옛 파일에 `Status: SUPERSEDED by ...` 표시.

## 8. UX 톤

- **존댓말 (해요체).** 게임 내 모든 인스트럭션·피드백은 존댓말. "공통인수를 찾아 끌어내세요" / "한 번 더 풀어볼까요" / "내일 또 봐요".
- **공유 OG 카드만 반말.** 친구 추천 맥락이라 "이거 봐봐", "5분 안에 풀림".
- **외재 보상 분위기 금지.** 폭죽, 축포, 🎉 이모지, 화려한 사운드 X. 정답 시 조용한 spring + glow만.
- **광고 카피 금지.** "Welcome to..." / "Unlock the power of..." 같은 generic copy는 즉시 다시 쓴다.
