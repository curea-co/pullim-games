# 05. 운영 로직 및 비즈니스 정책

## 5.1 핵심 비즈니스 규칙

### BR1. 학습효과 우선

게임화 메커닉이 학습효과 측정과 충돌하면 학습효과를 우선한다. 예: "스트릭이 끊기면 사용자 이탈"이 아니라 "스트릭 자체가 자기효능감을 깎으면 스트릭을 없앤다."

### BR2. 외재 보상 최소화

V1은 XP/레벨까지만. 그 이상의 보상 레이어(배지, 칭호, 가상화폐) 추가 시 명세 작성자 동의 필요.

### BR3. PVE만 허용

또래 비교 메커닉(랭킹, 매칭, 친구 도전, 점수 비교) V1에서 모두 금지. 본인 vs 본인 기록만 허용. SNS 공유는 자랑이 아닌 "같이 해보자" 톤.

### BR4. 5문제 1세션 고정

V1 한 세션 = 5문제. 시간 제한 X. 한 카드 풀이 시간은 무제한.

### BR5. FSRS가 카드 출제 결정자

사용자가 "어떤 카드 풀지" 선택 X. FSRS 우선순위 큐가 자동 결정. 단, 빈 큐 시 데모 모드 진입은 사용자 선택.

### BR6. 정답 판정은 equivalent form 인식

`x(2x+7) + 3` 같은 부분 변형도 인수분해 합법 경로면 정답 처리. AST 기반 equivalent form 매칭.

### BR7. Kill / Pivot 판정 (6주 시점)

V1 출시 후 6주에 4 신호 + 학습효과 신호 측정:
- 4 신호 중 3개 이상 + 학습효과 신호 통과 → V2 진입
- 4 신호 중 2개 또는 학습효과 신호 실패 → Pivot (메커닉/콘텐츠 변경)
- 4 신호 중 1개 이하 → Kill (명제 자체 재검토)

## 5.2 Auth / ACL 정책 (V1)

### 인증

- **V1 = 비로그인**. 사용자 식별은 browser fingerprint (UUID 기반 + canvas/font 보조 신호)
- 시크릿 모드, 브라우저 클리어 = 새로운 사용자로 인식 (silent failure 위험)
- 로그인/회원가입 화면 V1에 없음

### 데이터 접근 제어

- 모든 카드 풀, 5문제 시퀀스 = public (비로그인 누구나 접근)
- 본인 fingerprint 기반 진행도 = 같은 브라우저 세션 내에서만 조회
- 다른 사용자 데이터 조회 API 없음

### V2 확장 (메모용, V1 구현 X)

- Magic link 옵션 (이메일 1회 입력) → fingerprint와 합쳐 retrieval 데이터 보존
- 풀림 SSO 통합 → 풀림 계정과 fingerprint sync
- B2B 학교 도입 시 학교/학원 단위 인증

## 5.3 ERD / 데이터 모델

### Card (카드 마스터)

```
Card {
  id: UUID (PK)
  type: "factorization-block"   // V1 단일 type
  problem: {
    polynomial: string           // "2x² + 7x + 3"
    ast: PolynomialAST          // 파싱된 트리
    target_form: "factored"
  }
  difficulty_seed: 1..5          // 콘텐츠 큐레이터 할당
  unit: string                   // "고1-인수분해-공통인수"
  created_at: timestamp
  updated_at: timestamp
}
```

V1 = 5장 카드 (난이도 1~5 시드)
저장 = static JSON (V2부터 Vercel KV 마이그레이션 검토)

### CardState (사용자별 카드 상태)

```
CardState {
  fingerprint: string (PK1)
  card_id: UUID (PK2, FK → Card.id)
  R: float                       // retrievability 0~1
  S: float                       // stability (days)
  D: float                       // difficulty 1~10
  last_review_at: timestamp
  review_count: integer
  outcome_history: array         // ['pass', 'pass', 'fail', ...]
}
```

저장 = client-side localStorage (V1) + 서버 백업 (Vercel KV, V2)

### Session

```
Session {
  id: UUID (PK)
  fingerprint: string            // 익명 식별자
  started_at: timestamp
  ended_at: timestamp | null
  card_ids_attempted: UUID[]     // 5문제 시퀀스
  outcome: 'completed' | 'abandoned' | 'in_progress'
}
```

저장 = client-side + 서버 이벤트 로그

### Event (익명 이벤트 로깅)

```
Event {
  id: UUID (PK)
  session_id: UUID (FK)
  fingerprint: string
  card_id: UUID | null
  action: 'drag-start' | 'drag-end' | 'transform' | 'submit' | 'abandon'
  timestamp_ms: integer
  payload: JSONB                 // 인터랙션 정확도 측정용 (좌표, 시간 등)
}
```

저장 = `/api/event` POST → Vercel KV 또는 별도 분석 DB. PII 0.

## 5.4 Validation Rules

| 입력 | 검증 규칙 | 위반 시 |
|---|---|---|
| 카드 JSON 로드 | Zod 스키마 (id, type, problem, difficulty_seed) | 명시 에러 + 로깅 + fallback UI |
| 이벤트 payload | Zod 스키마 (action enum, timestamp_ms 양수, fingerprint format) | 422 응답 + 로깅 |
| Fingerprint format | UUID v4 또는 보조 신호 hash | 새 fingerprint 자동 생성 |
| AST 변형 결과 | round-trip 검증 (변형 후 다시 expand하면 원본 다항식과 equivalent) | 정답 인정 X, 재시도 가능 |
| 카드 difficulty_seed | 정수 1~5 | 카드 로드 거부 (콘텐츠 큐레이터 알림) |

## 5.5 데이터 보존 정책

- **익명 이벤트 로그**: 6개월 보존 후 자동 삭제 (V1 분석 기간 + 마진)
- **카드 마스터**: 영구 보존
- **CardState (localStorage)**: 사용자가 브라우저 클리어 시 자동 삭제
- **Session**: 6개월 보존

## 5.6 PII 정책 (V1)

- **수집 항목 0개.** 이름, 이메일, 전화번호, 학교, 학년 모두 수집 X
- **저장 항목**: browser fingerprint (보조 신호 포함), 인터랙션 좌표, 풀이 결과
- **만 14세 미만 처리**: V1 비로그인이라 정통망법 적용 안 됨. 로그인 도입 시 재검토
- **GDPR/CCPA**: 한국 서비스라 1차 적용 대상 아님. 글로벌 확장 시 재검토

### 출시 알림 신청 (V1.5 — Plan D Phase 2, **2026-05-20 정책 갱신**)

**핵심 원칙: 본 서버는 이메일 보존 0. 외부 메일 서비스에 즉시 위임.**

기존 hash-only 설계는 실제 알림 메일 발송이 불가능하다는 기능 모순(Codex 지적 #1)이 확인되어 **외부 메일 서비스 위임 모델**로 전환한다.

#### 데이터 흐름

```
클라이언트 (이메일 입력)
   │ plain email + source='billing-cta'
   ▼
/api/billing/notify  ← Zod strict 검증 (추가 필드 거부)
   │ Resend API 호출 (audience contact 등록)
   ▼
Resend (외부 메일 서비스, audience 보존)
   │ 응답 후 라우트 내 변수 폐기
   ▼
본 서버 DB·로그·메모리 잔존 0
```

#### 보안 boilerplate

- **본 서버 저장 0**: 라우트는 fetch 응답 처리 후 변수 폐기. DB·KV·파일·로그 어디에도 plain email 잔존하지 않음. `process.env.NODE_ENV !== "production"` 일 때도 email 자체는 로깅하지 않으며, 메타데이터(`source`, `ts`) 만 기록 가능.
- **Zod strict**: `BillingNotifySignupSchema.strict()` — 정의되지 않은 필드 동봉 시 422. raw email 외 식별자 누수 방지.
- **외부 위임 응답 폐기**: Resend 의 `id` 응답은 본 서버에서 보관 X (위임 후 외부에 권한 이양).
- **외부 서비스 6개월 보존 정책**: Resend audience 측 보관 정책 따름. 사용자가 unsubscribe 시 Resend dashboard 에서 제거 — 본 서버 액션 0.
- **same-origin 가드** (2026-05-20 round 3 fix — Codex 지적 #2): 라우트는 `Origin` 또는 `Referer` 헤더가 본 사이트 origin(`NEXT_PUBLIC_SITE_ORIGIN`·`VERCEL_URL`·요청 host 중 하나) 와 일치할 때만 처리. 외부 도메인 cross-origin POST 는 403 거부.
- **Rate limit** (2026-05-20 round 3 fix): IP 별 **1분 5회 + 1시간 10회** 인메모리 sliding window. Resend 무료 한도(100/일) 의 abuse 벡터 차단. 인프라 의존 0 (SPEC §09 원칙). 분산 환경 정밀 limit 은 V2 결제 진입 시 KV 도입과 함께 재설계. BR-PAY3 학생 보호와도 일치 — 익명 abuser 가 학생 이메일을 대량 주입하지 못함.
- **중복 등록 idempotent** (2026-05-20 round 3·5·7 fix — Codex 지적 #1): Resend 응답 중 **HTTP 409 Conflict**, 또는 4xx 응답 body 가 `\balready\s+exists\b` 정규식(대소문자 무시, 두 단어 인접 매칭) 에 일치할 때만 → 사용자 관점 success 처리. `already` / `exists` 단독 substring 매칭은 false positive(`audience does not exists` 등) 가 발생하므로 사용하지 않는다. 같은 이메일 재신청해도 "신청 실패" 가 영구 노출되지 않음. 기타 4xx(validation·auth) 는 502, 5xx 도 502, secret 미설정은 503.

#### 사용자 안내 카피

"출시 시 알림을 받기 위해 신청됐어요. 입력하신 이메일은 알림 발송용 외부 서비스(Resend)로 즉시 위임되어 보관되며, 출시 알림 외 용도로는 사용하지 않습니다. 풀림 서버에는 이메일이 저장되지 않아요."

### 5.7.5 외부 메일 서비스 위임 정책 (2026-05-20 합의 — Codex 지적 #1 fix)

**채택**: **Resend** (단일 메일 서비스).

#### 결정 배경

PR #91 1차 구현은 클라이언트 sha256 hash 만 받는 hash-only 모델이었으나, Codex review 가 **단방향 hash 로는 실제 출시 알림 메일 발송이 불가능** 하다는 기능 모순을 지적했다. 사용자 합의: 본 서버 PII 0 원칙은 유지하되, **외부 메일 서비스에 즉시 위임** 하여 발송 가능성을 확보한다 (옵션 C 채택).

#### 4 axis 비교 매트릭스

| 서비스 | KR 접근성 | 무료 한도 | API 단순도 | 통합 LOC 추정 | 결정 |
|---|---|---|---|---|---|
| **Resend** | 한국 IP 직접 호출 OK, 도메인·SPF·DKIM 표준 | **100/일 무료**, 도메인 1개 검증 후 즉시 | REST 1엔드포인트 (`POST /audiences/.../contacts`), JSON body | ≈30 LOC + env 1개 | **채택** |
| Mailchimp | KR 접근 OK 단 audience 관리 UI 복잡, SDK 무거움 | 500 contacts 무료 단 발송 횟수 제약 | OAuth 또는 API key, audience id·status·tags 다단계 | ≈120 LOC | 보류 (오버엔지) |
| SendGrid | KR 접근 OK, Twilio 인증 단계 추가 | 100/일 무료 (Marketing Campaigns 별) | API key + contact lists 별 분리 | ≈80 LOC | 보류 |
| Postmark | KR 접근 OK, 트랜잭션 메일 특화 | 100/월 무료 (테스트 한도 낮음) | 단순 API 단 audience 개념 X — broadcasts 별도 | ≈50 LOC | 보류 (audience 모델 X) |

**선택 사유** (결단력 룰 — 갈래 묻지 X, 1순위 명시):
1. **무료 한도 충분** (100/일 = V2 출시 전 알림 수집 기간 ≈3000 신청자 커버)
2. **API 단순도 최상** — fetch 직접 호출 1줄, SDK 의존성 0 (보안·번들 사이즈 보존)
3. **audience 모델 일치** — "관심자 명단" → 출시 시 단일 broadcast 발송 패턴이 본 use case 와 1:1 매칭
4. **KR 직접 호출** — 프록시·CDN 우회 없이 한국 vercel edge function 에서 직접 호출 가능

#### Secret 관리

- 환경변수: `RESEND_API_KEY` — Vercel project secret 으로 등록
- 환경변수: `RESEND_AUDIENCE_ID` — Resend dashboard 에서 audience 생성 후 id 등록
- 환경변수: `NEXT_PUBLIC_SITE_ORIGIN` — same-origin 가드 (운영·preview 별 명시. dev 는 자동 fallback)
