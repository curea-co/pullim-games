# 05. 운영 로직 및 비즈니스 정책

## 5.1 핵심 비즈니스 규칙

### BR1. 학습효과 우선

게임화 메커닉이 학습효과 측정과 충돌하면 학습효과를 우선한다. 예: "스트릭이 끊기면 사용자 이탈"이 아니라 "스트릭 자체가 자기효능감을 깎으면 스트릭을 없앤다."

### BR2. 외재 보상 최소화

V1은 XP/레벨까지만. 그 이상의 보상 레이어(배지, 칭호, 가상화폐) 추가 시 명세 작성자 동의 필요.

### BR3. PVE만 허용

또래 비교 메커닉(랭킹, 매칭, 친구 도전, 점수 비교) V1에서 모두 금지. 본인 vs 본인 기록만 허용. SNS 공유는 자랑이 아닌 "같이 해보자" 톤.

### BR4. 5문제 1세션 고정

V1 한 세션 = 5문제. 시간 제한 X. 한 카드 풀이 시간은 무제한.

### BR5. FSRS가 카드 출제 결정자

사용자가 "어떤 카드 풀지" 선택 X. FSRS 우선순위 큐가 자동 결정. 단, 빈 큐 시 데모 모드 진입은 사용자 선택.

### BR6. 정답 판정은 equivalent form 인식

`x(2x+7) + 3` 같은 부분 변형도 인수분해 합법 경로면 정답 처리. AST 기반 equivalent form 매칭.

### BR7. Kill / Pivot 판정 (6주 시점)

V1 출시 후 6주에 4 신호 + 학습효과 신호 측정:
- 4 신호 중 3개 이상 + 학습효과 신호 통과 → V2 진입
- 4 신호 중 2개 또는 학습효과 신호 실패 → Pivot (메커닉/콘텐츠 변경)
- 4 신호 중 1개 이하 → Kill (명제 자체 재검토)

## 5.2 Auth / ACL 정책 (V1.x — 2026-05-29 개정)

> **개정 이력**: 본 절은 원래 "V1 = 비로그인, 로그인/회원가입 V1에 없음"이었다. 2026-05-29 사용자(G1) 합의로 **선택적 계정(이메일+비밀번호 로그인/회원가입)**을 도입한다. 근거·절차: `proc/plan/2026-05-29_auth-login-signup.md` (거버넌스: spec 우선 개정 → 코드). games·games-arcade는 **완전 독립 계정**(풀림 플랫폼 통합 유저 테이블 미사용).

### 인증

- **비로그인 우선 + 선택적 계정**. 익명 사용자는 browser fingerprint (UUID 기반 + canvas/font 보조 신호)로 계속 무마찰 플레이 가능 — 가입 강요 없음.
- **선택적 계정(이메일+비밀번호)**: 사용자가 원하면 가입해 안정적인 계정 신원을 갖는다.
  - 비밀번호: bcryptjs 해시. 세션: opaque 토큰 + HttpOnly 쿠키(7일). JWT 미사용.
  - 로그인 시 현재 fingerprint를 계정에 연결(`fingerprint_links`) — 이후 학습 데이터 서버 귀속/다기기 동기화의 **토대**.
  - ⚠️ **현 단계 범위**: 서버에 영속되는 것은 `users`/`auth_sessions`/`fingerprint_links` 뿐. **SRS·스트릭·커스텀 콘텐츠는 아직 localStorage 전용** — 학습 데이터의 서버 보존/다기기 동기화는 **후속 phase**(`proc/plan/2026-05-29_auth-login-signup.md` 비범위). 따라서 현 시점 계정은 "데이터가 자동 복구된다"고 약속하지 않는다.
- 시크릿 모드, 브라우저 클리어 = (익명) 새로운 사용자로 인식. 계정이 있어도 **현재는 학습 데이터가 자동 복구되지 않는다**(위 후속 phase 완료 후 가능).

### 데이터 접근 제어

- 모든 카드 풀, 5문제 시퀀스 = public (비로그인 누구나 접근)
- 본인 fingerprint 기반 진행도 = 같은 브라우저 세션 내에서만 조회
- 다른 사용자 데이터 조회 API 없음

### V2 확장 (메모용, V1 구현 X)

- Magic link 옵션 (이메일 1회 입력) → fingerprint와 합쳐 retrieval 데이터 보존
- 풀림 SSO 통합 → 풀림 계정과 fingerprint sync
- B2B 학교 도입 시 학교/학원 단위 인증

## 5.3 ERD / 데이터 모델

### Card (카드 마스터)

```
Card {
  id: UUID (PK)
  type: "factorization-block"   // V1 단일 type
  problem: {
    polynomial: string           // "2x² + 7x + 3"
    ast: PolynomialAST          // 파싱된 트리
    target_form: "factored"
  }
  difficulty_seed: 1..5          // 콘텐츠 큐레이터 할당
  unit: string                   // "고1-인수분해-공통인수"
  created_at: timestamp
  updated_at: timestamp
}
```

V1 = 5장 카드 (난이도 1~5 시드)
저장 = static JSON (V2부터 Vercel KV 마이그레이션 검토)

### CardState (사용자별 카드 상태)

```
CardState {
  fingerprint: string (PK1)
  card_id: UUID (PK2, FK → Card.id)
  R: float                       // retrievability 0~1
  S: float                       // stability (days)
  D: float                       // difficulty 1~10
  last_review_at: timestamp
  review_count: integer
  outcome_history: array         // ['pass', 'pass', 'fail', ...]
}
```

저장 = client-side localStorage (V1) + 서버 백업 (Vercel KV, V2)

### Session

```
Session {
  id: UUID (PK)
  fingerprint: string            // 익명 식별자
  started_at: timestamp
  ended_at: timestamp | null
  card_ids_attempted: UUID[]     // 5문제 시퀀스
  outcome: 'completed' | 'abandoned' | 'in_progress'
}
```

저장 = client-side + 서버 이벤트 로그

### Event (익명 이벤트 로깅)

```
Event {
  id: UUID (PK)
  session_id: UUID (FK)
  fingerprint: string
  card_id: UUID | null
  action: 'drag-start' | 'drag-end' | 'transform' | 'submit' | 'abandon'
  timestamp_ms: integer
  payload: JSONB                 // 인터랙션 정확도 측정용 (좌표, 시간 등)
}
```

저장 = `/api/event` POST → Vercel KV 또는 별도 분석 DB. PII 0.

## 5.4 Validation Rules

| 입력 | 검증 규칙 | 위반 시 |
|---|---|---|
| 카드 JSON 로드 | Zod 스키마 (id, type, problem, difficulty_seed) | 명시 에러 + 로깅 + fallback UI |
| 이벤트 payload | Zod 스키마 (action enum, timestamp_ms 양수, fingerprint format) | 422 응답 + 로깅 |
| Fingerprint format | UUID v4 또는 보조 신호 hash | 새 fingerprint 자동 생성 |
| AST 변형 결과 | round-trip 검증 (변형 후 다시 expand하면 원본 다항식과 equivalent) | 정답 인정 X, 재시도 가능 |
| 카드 difficulty_seed | 정수 1~5 | 카드 로드 거부 (콘텐츠 큐레이터 알림) |

## 5.6 PII 정책 (V1.x — 2026-05-29 개정)

> **개정 이력**: 선택적 계정 도입(§5.2)으로 PII 수집이 발생한다. 익명 사용자는 PII 0 유지, 계정 사용자만 이메일 수집. 근거: `proc/plan/2026-05-29_auth-login-signup.md`.

- **익명 사용자: 수집 항목 0개.** 이름·이메일·전화·학교·학년 수집 X. 저장 = browser fingerprint, 인터랙션 좌표, 풀이 결과.
- **계정 사용자 저장 항목: 이메일 + 비밀번호 해시 + (연결된) browser fingerprint.** 가입/로그인 시 현재 fingerprint를 계정에 귀속(`fingerprint_links`)한다. 이름·전화·학교·학년은 계정에서도 수집 X (PII 최소화 유지). 비밀번호는 평문 저장 금지(bcryptjs 해시).
- **만 14세 미만 처리**: 계정(로그인) 도입 = 정보통신망법 적용 트리거. 가입 시 만 14세 이상 확인(미만은 법정대리인 동의 절차 — 후속 phase). 익명 플레이는 계속 정통망법 비대상.
- **GDPR/CCPA**: 한국 서비스라 1차 적용 대상 아님. 글로벌 확장 시 재검토.

### 출시 알림 신청 (V1.5 — Plan D Phase 2, **2026-05-20 정책 갱신**)

**핵심 원칙: 본 서버는 이메일 보존 0. 외부 메일 서비스에 즉시 위임.**

기존 hash-only 설계는 실제 알림 메일 발송이 불가능하다는 기능 모순(Codex 지적 #1)이 확인되어 **외부 메일 서비스 위임 모델**로 전환한다.

#### 데이터 흐름

```
클라이언트 (이메일 입력)
   │ plain email + source='billing-cta'
   ▼
/api/billing/notify  ← Zod strict 검증 (추가 필드 거부)
   │ Resend API 호출 (audience contact 등록)
   ▼
Resend (외부 메일 서비스, audience 보존)
   │ 응답 후 라우트 내 변수 폐기
   ▼
본 서버 DB·로그·메모리 잔존 0
```

#### 보안 boilerplate

- **본 서버 저장 0**: 라우트는 fetch 응답 처리 후 변수 폐기. DB·KV·파일·로그 어디에도 plain email 잔존하지 않음. 환경 무관 (production 포함) email 원문 로깅 0 — 메타데이터(`source`, `ts`, `reason`, `status`) 만 기록한다.
- **Zod strict**: `BillingNotifySignupSchema.strict()` — 정의되지 않은 필드 동봉 시 422. raw email 외 식별자 누수 방지.
- **외부 위임 응답 폐기**: Resend 의 `id` 응답은 본 서버에서 보관 X (위임 후 외부에 권한 이양).
- **외부 서비스 6개월 보존 정책**: Resend audience 측 보관 정책 따름. 사용자가 unsubscribe 시 Resend dashboard 에서 제거 — 본 서버 액션 0.
- **same-origin 가드** (2026-05-20 round 3 fix — Codex 지적 #2): 라우트는 `Origin` 또는 `Referer` 헤더가 본 사이트 origin(`NEXT_PUBLIC_SITE_ORIGIN`·`VERCEL_URL`·요청 host 중 하나) 와 일치할 때만 처리. 외부 도메인 cross-origin POST 는 403 거부. **헤더만으로는 spoof 가능하므로 다음 CSRF 토큰 가드와 함께 다층 적용**.
- **CSRF 토큰 (SameSite=Strict 쿠키)** (2026-05-21 round 10 fix — Codex 지적 #1): `Origin`·`Referer` 헤더는 비브라우저 클라이언트가 쉽게 위조 가능해 헤더 단독 가드만으로는 외부 남용 차단 효과가 약하다. 추가 가드로 `GET /api/billing/notify/csrf` 가 1회용 nonce 를 `SameSite=Strict; HttpOnly; Secure(production); Path=/api/billing/notify; Max-Age=3600` 쿠키로 발급한다. POST 요청 시 라우트가 쿠키에서 토큰 추출 → in-memory store 일치 검증 → 통과 시 1회 소비. SameSite=Strict 가 cross-origin POST 에 쿠키를 동봉하지 않으므로 curl/봇 이 헤더만 spoof 해도 nonce 부재(`missing`) 또는 형식 위조(`invalid`) 로 403. 토큰은 32 byte random hex(64 chars), TTL 1시간, 1회 소비(replay 차단). nonce store 는 모듈 스코프 Map — cold start 시 reset 되지만 폼 진입 직후 사용되는 본 use case 특성상 충분. V2 진입 시 KV 기반 stateless 토큰으로 재설계.
- **Rate limit — 3-tier NAT 친화 + Resend 일일 한도 정합** (2026-05-21 round 9·10 fix — Codex 지적 #2):
  - **tier 1 (IP 만, 분·시간)**: 30/분 + 100/시간. 학교/학원/가정 NAT 처럼 공인 IP 1개를 여러 학생이 공유하는 환경 친화. 기존 5/분 한도는 같은 NAT 안 학생이 서로를 429 로 막는 거짓 양성을 유발해 폐기.
  - **tier 2 (IP + email 해시, 시간)**: 6/시간. 같은 IP·같은 이메일 abuse 만 좁게 차단. email 해시는 normalize(lowercase + trim) 후 SHA-256(16 chars) — **rate-limit Map 의 bucket key 로만 in-memory 잔존**, DB·KV·로그·외부 위임 어디에도 저장하지 않음 (PII 0 유지). 시간 경과 시 GC.
  - **tier 3 (IP·글로벌 일일, Resend 100/일 정합 — round 10 fix #2)**:
    - **IP 일일 한도**: 20/일/IP. 단일 IP 가 Resend 무료 한도(100/일) 의 20% 이상을 단독으로 소진하지 못하도록 cap. 학교 NAT 100명 × 4명 동의 = 400/일 시나리오에서도 IP 하나당 20건만 통과 → 5개 IP 분산 시 100건 정상 처리.
    - **글로벌 일일 cap**: 80/일. Resend 무료 한도의 80% — 20% 안전 마진 확보. 도달 시 정상 사용자도 429 차단하지만 quota exhaustion 으로 알림 수집 마비되는 것보단 fail-closed 가 안전.
    - **Soft warning 임계**: 글로벌 60/일 도달 시 `console.warn('[billing/notify] daily quota soft-warning', { marker: 'daily_quota_soft_warning', dayKey, globalCount, cap, warnThreshold })` 마커 1회 — 운영 측이 quota cap 도달 전 단계에서 인지 가능.
    - day key 는 UTC `YYYY-MM-DD` 기반. 자정마다 자동 reset.
  - tier 1·tier 3 은 본문 파싱 전 적용(invalid-body 폭주 abuse 차단), tier 2 는 Zod 검증 후 적용(email 필요).
  - Resend 무료 한도(100/일) 보호 + BR-PAY3 학생 보호 (같은 이메일 abuse 대량 주입 차단).
  - 분산 환경 정밀 limit 은 V2 결제 진입 시 KV 도입과 함께 재설계 (cold start 시 카운터 reset 한계).
- **중복 등록 idempotent** (2026-05-20 round 3·5·7 fix — Codex 지적 #1): Resend 응답 중 **HTTP 409 Conflict**, 또는 4xx 응답 body 가 `\balready\s+exists\b` 정규식(대소문자 무시, 두 단어 인접 매칭) 에 일치할 때만 → 사용자 관점 success 처리. `already` / `exists` 단독 substring 매칭은 false positive(`audience does not exists` 등) 가 발생하므로 사용하지 않는다. 같은 이메일 재신청해도 "신청 실패" 가 영구 노출되지 않음. 기타 4xx(validation·auth) 는 502, 5xx 도 502, secret 미설정은 503.
- **Production 관측 신호** (2026-05-21 round 9 fix — Codex 지적 #3): Resend 위임 실패(502·503) 시 `console.error('[billing/notify] resend delegation failed', { source, ts, reason, status, marker })` 형태의 구조화 로그를 환경 무관(production 포함) 으로 남긴다. `marker` 는 `secret_missing`(503·RESEND_API_KEY 부재) 과 `external_error`(502·외부 4xx/5xx/network) 를 구분해 Vercel 로그에서 grep 가능. email 원문은 어떤 형태로도 포함되지 않는다 — PII 0 정책 보존.

### 5.7.5 외부 메일 서비스 위임 정책 (2026-05-20 합의 — Codex 지적 #1 fix)

**채택**: **Resend** (단일 메일 서비스).

#### 결정 배경

PR #91 1차 구현은 클라이언트 sha256 hash 만 받는 hash-only 모델이었으나, Codex review 가 **단방향 hash 로는 실제 출시 알림 메일 발송이 불가능** 하다는 기능 모순을 지적했다. 사용자 합의: 본 서버 PII 0 원칙은 유지하되, **외부 메일 서비스에 즉시 위임** 하여 발송 가능성을 확보한다 (옵션 C 채택).

3. **audience 모델 일치** — "관심자 명단" → 출시 시 단일 broadcast 발송 패턴이 본 use case 와 1:1 매칭
4. **KR 직접 호출** — 프록시·CDN 우회 없이 한국 vercel edge function 에서 직접 호출 가능

#### Secret 관리 (round 8 — 글로벌 Contacts 모델 정합)

- 환경변수 `RESEND_API_KEY` — Vercel project secret 으로 등록. **필수** — 미설정 시 503.
- 환경변수 `RESEND_SEGMENT_ID` — 선택. 설정 시 contact 생성 페이로드에 `segments: [{ id }]` 동봉돼 즉시 해당 segment 에 추가된다. 미설정 시 `properties.source` 마커만으로 캠페인 분리.
- 환경변수 `RESEND_AUDIENCE_ID` — **deprecated** (round 8). 이전 `audiences/{id}/contacts` 경로용. 글로벌 Contacts 모델에서는 미사용. 환경에 남아 있어도 신경로는 무시.
- 환경변수 `NEXT_PUBLIC_SITE_ORIGIN` — same-origin 가드 (운영·preview 별 명시. dev 는 자동 fallback).
- 키 미설정 시 (개발·테스트·CI): 라우트는 422 가 아닌 **503 service_unavailable** 응답으로 외부 의존성 단절을 명시. 단 schema 검증은 통과 후 동작.

#### 캠페인 분리 마커 (round 8 — Codex 지적 #3 fix)

본 라우트가 생성하는 모든 contact 에 다음 `properties` 가 동봉된다:

```json
{
  "properties": {
    "source": "billing-launch-notify",
    "consented_at": "2026-05-20T07:30:00.000Z"
  }
}
```

**운영상 강제 수단**:
- 출시 broadcast 발송 시 `properties.source = 'billing-launch-notify'` 만 필터링해 발송 대상 결정.
- 다른 캠페인이 같은 Resend workspace 를 공유해도 본 source 외 contact 는 사용 금지.
- `consented_at` 은 동의 시점 기록 — 추후 GDPR-style 동의 추적·삭제 요청 응대에도 사용 가능.
- 본 마커 룰을 운영 측에서 강제 위반하면 SPEC §05.7.5 위반으로 처리 — "출시 알림 외 용도로는 사용하지 않는다" 약속은 본 마커 기준으로 검증된다.

상수 정의: `src/lib/server/billing/resend-client.ts#BILLING_SOURCE_MARKER`.

| CSRF 토큰 부재·만료·위조 (round 10 fix #1) | 호출 0 | 403 forbidden_csrf | (브라우저 폼에선 발생 X — GET 사전 호출 강제) |
| Schema 위반 (필드 누락·strict 위반) | 호출 0 | 422 | "신청 실패, 잠시 후" |

> **round 8 #2 — 재구독 보장 정합**: POST 가 중복으로 막힌 경우 단순 success 가 아닌 PATCH 로 `unsubscribed: false` + `properties.source` 를 idempotent 재set 한다. 과거 `unsubscribed: true` 상태로 잔존한 contact 가 출시 broadcast 발송 대상에서 제외되는 거짓 success 를 막는다.
