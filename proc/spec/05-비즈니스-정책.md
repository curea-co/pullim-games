# 05. 운영 로직 및 비즈니스 정책

## 5.1 핵심 비즈니스 규칙

### BR1. 학습효과 우선

게임화 메커닉이 학습효과 측정과 충돌하면 학습효과를 우선한다. 예: "스트릭이 끊기면 사용자 이탈"이 아니라 "스트릭 자체가 자기효능감을 깎으면 스트릭을 없앤다."

### BR2. 외재 보상 최소화

V1은 XP/레벨까지만. 그 이상의 보상 레이어(배지, 칭호, 가상화폐) 추가 시 명세 작성자 동의 필요.

### BR3. PVE만 허용

또래 비교 메커닉(랭킹, 매칭, 친구 도전, 점수 비교) V1에서 모두 금지. 본인 vs 본인 기록만 허용. SNS 공유는 자랑이 아닌 "같이 해보자" 톤.

### BR4. 5문제 1세션 고정

V1 한 세션 = 5문제. 시간 제한 X. 한 카드 풀이 시간은 무제한.

### BR5. FSRS가 카드 출제 결정자

사용자가 "어떤 카드 풀지" 선택 X. FSRS 우선순위 큐가 자동 결정. 단, 빈 큐 시 데모 모드 진입은 사용자 선택.

### BR6. 정답 판정은 equivalent form 인식

`x(2x+7) + 3` 같은 부분 변형도 인수분해 합법 경로면 정답 처리. AST 기반 equivalent form 매칭.

### BR7. Kill / Pivot 판정 (6주 시점)

V1 출시 후 6주에 4 신호 + 학습효과 신호 측정:
- 4 신호 중 3개 이상 + 학습효과 신호 통과 → V2 진입
- 4 신호 중 2개 또는 학습효과 신호 실패 → Pivot (메커닉/콘텐츠 변경)
- 4 신호 중 1개 이하 → Kill (명제 자체 재검토)

## 5.2 Auth / ACL 정책 (V1.x — 2026-07-04 개정)

> **개정 이력**: 본 절은 원래 "V1 = 비로그인, 로그인/회원가입 V1에 없음"이었다. 2026-05-29 G1 합의로 **선택적 계정(이메일+비밀번호)** 도입(`proc/plan/2026-05-29_auth-login-signup.md`). **2026-06-01 G1 합의로 입구 인증 모델(arcade 미러)로 전환** — "비로그인 무마찰(신원 없이 즉시 플레이)"을 **"입구 신원 필수"**로 개정(`proc/plan/2026-06-01_arcade-entry-model.md`). **2026-06-05 G1 합의로 학습 데이터 서버 동기화 정책 확정**(구현은 후속 phase) — 계정 사용자에 한해 SRS·스트릭·activity_log·커스텀의 서버 영속/다기기 복구 허용(`proc/plan/2026-06-05_learning-data-server-sync.md`). **2026-07-04 G1 합의로 회원 신원을 pullim-web/pullim-api 중앙 인증(SSO)으로 위임**(`proc/plan/2026-07-03_games-unified-login-os-delegation.md`, §5.2 V2 확장의 "풀림 SSO 통합"을 V1.x로 승격) — ⑴ **회원**은 `.pullim.ai` 공유 쿠키 세션(pullim-api 발급 ES256, `Domain=.pullim.ai`, HttpOnly)으로 통일, 미인증 회원 진입은 pullim-web `/login?next=<games url>`로 위임, ⑵ **게스트는 games 독립 유지**(localStorage 프로필, 서버 전송 0 — 무변경), ⑶ **학습 데이터는 games 전용 Postgres 존치**하되 회원 신원 키만 pullim-api `sub`로 재배선(데이터 이관·DB 폐기 아님). games 자체 email+비밀번호 인증은 **legacy dormant**(env `NEXT_PUBLIC_DOMAIN_API_URL` 토글로 pullim 모드↔legacy 분기, 코드 보존·완전 제거 아님). → **"완전 독립 계정" 조항은 데이터 소유(games DB 존치)·게스트 독립에 한정으로 축소**되고, 회원 신원(계정·세션 발급·검증)은 pullim-api 중앙 소유로 이동. arcade 등 sibling 서비스의 세션 재사용(묵시적 계정 통합)은 audience/스코프로 차단(구체 격리 계약은 pullim-api 관할).

### 인증 (입구 신원 모델 — arcade 미러)

- **입구에서 게스트/회원을 구분해 받는다.** 랜딩(`/`)에서 [회원가입]·[로그인](회원 경로) 또는 [게스트로 시작 → `/start`](게스트 경로)로 갈린다.
- **신원 = 게스트 프로필(localStorage) OR 로그인 계정.** 둘 중 하나라도 있어야 **대시보드(`/home`)·게임 플레이** 접근 가능. 신원 없으면 랜딩으로 리다이렉트. (랜딩·게임 허브 브라우징은 열림.)
- **게스트 프로필**: 가입 없이 **닉네임 + 학년**(+ 만14세 자가확인)으로 생성(`pullim-games:player`). browser fingerprint는 이 게스트 신원의 **부속 신호**(진행도 귀속). "무마찰"은 *완전 익명*이 아니라 *가입 없는 게스트 신원 생성*으로 재정의.
- **선택적 계정(회원 신원)**: 사용자가 원하면 로그인해 안정적인 계정 신원을 갖는다. **2026-07-04 개정 — 회원 신원은 pullim-api 중앙 인증(SSO)으로 위임**(pullim 모드):
  - **pullim 모드(정본, env `NEXT_PUBLIC_DOMAIN_API_URL` 설정 시)**: 회원 세션 = pullim-api 발급 `.pullim.ai` 공유 쿠키(`__Secure-<env>-pullim-at`, ES256, HttpOnly). 로그인/가입 UI 는 games 가 보유하지 않고 pullim-web `/login·/signup`으로 위임(가입·본인인증 권위 중앙 — §5.6). games 는 세션 검증을 pullim-api `GET /games/me` introspection(200=인증/401=미인증, games flag 무관 — 플레이 무료)으로 하고, `sub`를 학습 데이터 key 로 쓴다. games 로컬 세션 저장·검증 없음.
  - **legacy 모드(env 미설정 시, dormant)**: 기존 games 자체 인증 — 비밀번호 bcryptjs 해시, opaque 토큰 + HttpOnly 쿠키(`pullim_games_session`, 7일, host-only), JWT 미사용. **코드 보존·완전 제거 아님**(pullim 모드 롤백 안전판). 완전 은퇴는 별 PR·명시 승인 후.
  - 로그인 시 현재 fingerprint를 계정에 연결(`fingerprint_links`) — 이후 학습 데이터 서버 귀속/다기기 동기화의 **토대**. **연결 정책 = first-writer-wins**: fingerprint 는 **처음 귀속한 계정이 소유**하며, 같은 브라우저에서 다른 계정이 로그인해도 자동 재귀속하지 않는다(공유 기기 silent 재귀속 방지). 계정 간 명시적 이전은 후속 phase. (pullim 모드에서 계정 = pullim-api `sub`.)
  - **학습 데이터 서버 영속(2026-06-05 G1 정책 확정. 서버 구현 P1~P3 적재 #117, 클라 연결 P4 후속)**: **계정 사용자에 한해** SRS(카드상태)·스트릭·**활동로그(activity_log)**·커스텀 콘텐츠를 games 전용 Postgres에 영속·다기기 동기화(§5.5/§5.6과 동일 4종 — 보존기간만 상이, activity_log는 14일). **익명/게스트 사용자는 현행 그대로 localStorage 전용**(서버 전송 0). 동기화 정책: 로컬 우선(localStorage 캐시) + 서버 백업, 로그인 시 증분 pull·쓰기 시 배치 push, 다기기 충돌은 자동 머지(SRS·커스텀은 데이터 recency 기준 조건부 — 오래된 payload 무시, 롤백 금지; best-effort). ⚠️ **현재 서버 엔드포인트(`/api/sync`)는 존재하나 이를 호출하는 클라(P4)가 아직 없어 사용자 노출 동작 변화는 없다**(런타임상 익명/게스트와 동일하게 localStorage 동작). 근거: `proc/plan/2026-06-05_learning-data-server-sync.md`. **⚠️ 2026-07-04 개정 — 저장 위치는 games 전용 Postgres 그대로 존치**(pullim-api 이관·DB 폐기 아님). pullim 모드에서 바뀌는 것은 **회원 식별 key 뿐**: games 자체 `user_id` → pullim-api `sub`(`/games/me` introspection 결과). 학습데이터 스키마·`/api/sync` semantics·보존기간 무변경(`proc/plan/2026-07-03_games-unified-login-os-delegation.md` D3).
  - 익명→계정 흡수는 **사용자 확인 후에만** 수행(공유 기기 명의오염 방지). 자동 흡수 금지.
- 시크릿 모드, 브라우저 클리어 = (익명/게스트) 새로운 사용자로 인식. **계정 로그인 시 학습 데이터가 서버에서 다기기 복구되도록 한다**(2026-06-05 정책 확정 — SRS·스트릭·activity_log·커스텀; **구현은 후속 phase라 현재는 자동 복구 없음**, 게스트 프로필의 서버 귀속도 후속 phase).

### 데이터 접근 제어

- 모든 카드 풀, 5문제 시퀀스 = public (단 플레이는 입구 신원 필요 — 게스트/회원)
- **게스트(비회원) 진행도** = fingerprint/게스트 기반, **같은 브라우저 세션 내에서만 조회**(서버 미저장, 현행 유지)
- **계정 사용자 학습 데이터**(2026-06-05 정책, 후속 구현) = 서버(`WHERE user_id`)에 본인 것만 귀속·조회, **로그인하면 다기기 복구**. cross-user 조회 경로 0
- 다른 사용자 데이터 조회 API 없음(계정·게스트 공통)

### V2 확장 (메모용, V1 구현 X)

- Magic link 옵션 (이메일 1회 입력) → fingerprint와 합쳐 retrieval 데이터 보존
- 풀림 SSO 통합 → 풀림 계정과 fingerprint sync
- B2B 학교 도입 시 학교/학원 단위 인증

## 5.3 ERD / 데이터 모델

### Card (카드 마스터)

```
Card {
  id: UUID (PK)
  type: "factorization-block"   // V1 단일 type
  problem: {
    polynomial: string           // "2x² + 7x + 3"
    ast: PolynomialAST          // 파싱된 트리
    target_form: "factored"
  }
  difficulty_seed: 1..5          // 콘텐츠 큐레이터 할당
  unit: string                   // "고1-인수분해-공통인수"
  created_at: timestamp
  updated_at: timestamp
}
```

V1 = 5장 카드 (난이도 1~5 시드)
저장 = static JSON (V2부터 Vercel KV 마이그레이션 검토)

### CardState (사용자별 카드 상태)

```
CardState {
  fingerprint: string (PK1)
  card_id: UUID (PK2, FK → Card.id)
  R: float                       // retrievability 0~1
  S: float                       // stability (days)
  D: float                       // difficulty 1~10
  last_review_at: timestamp
  review_count: integer
  outcome_history: array         // ['pass', 'pass', 'fail', ...]
}
```

저장 = client-side localStorage(1차) + **계정 사용자 서버 백업 = games 전용 Postgres**(2026-06-05 정책 확정, **후속 구현 예정** — Vercel KV 아님, auth가 이미 Postgres 채택). 익명/게스트는 localStorage 전용. 근거: `proc/plan/2026-06-05_learning-data-server-sync.md`.

> ⚠️ **모델 정의 정합(2026-06-05)**: 위 CardState ERD(`fingerprint`+`card_id` 2키)는 **익명/게스트 localStorage 모델**이다. **계정 사용자 서버 스키마는 다르다**(후속 구현): 학습 데이터 4종이 `user_id` 스코프로 각각 별도 테이블 —
> - `srs_states(user_id, game_id, card_id, fsrs_card JSONB, review_count, last_review_at, updated_at)` — PK `(user_id, game_id, card_id)`
> - `streaks(user_id PK, current, longest, last_active_date, updated_at)`
> - `activity_log(user_id, game_id, date, device_id, count, updated_at)` — per-device 절대 카운터(`device_id`=동기화 전용 랜덤 UUID, fingerprint 아님), 표시값=SUM, **14일 retention·집계는 `date` 버킷 기준**(§5.5 — `updated_at` 기준이면 오래된 date 부활, #117 정정). `updated_at`(epoch)=LWW write 시각 기록용. 서버 주기 cleanup(date<cutoff)
> - `custom_content(user_id PK, snapshot JSONB, updated_at)` — 컬렉션 스냅샷
>
> 전부 `ON DELETE CASCADE`. cross-user 노출 0(모든 쿼리 `WHERE user_id`). 권위 스키마 정의는 `proc/plan/2026-06-05_learning-data-server-sync.md` §4.2. (서버 SRS 는 `fingerprint` 가 아니라 `user_id` 로 귀속 — 익명 모델과 키가 다름.)

### Session

```
Session {
  id: UUID (PK)
  fingerprint: string            // 익명 식별자
  started_at: timestamp
  ended_at: timestamp | null
  card_ids_attempted: UUID[]     // 5문제 시퀀스
  outcome: 'completed' | 'abandoned' | 'in_progress'
}
```

저장 = client-side + 서버 이벤트 로그

### Event (익명 이벤트 로깅)

```
Event {
  id: UUID (PK)
  session_id: UUID (FK)
  fingerprint: string
  card_id: UUID | null
  action: 'drag-start' | 'drag-end' | 'transform' | 'submit' | 'abandon'
  timestamp_ms: integer
  payload: JSONB                 // 인터랙션 정확도 측정용 (좌표, 시간 등)
}
```

저장 = `/api/event` POST → Vercel KV 또는 별도 분석 DB. PII 0.

## 5.4 Validation Rules

| 입력 | 검증 규칙 | 위반 시 |
|---|---|---|
| 카드 JSON 로드 | Zod 스키마 (id, type, problem, difficulty_seed) | 명시 에러 + 로깅 + fallback UI |
| 이벤트 payload | Zod 스키마 (action enum, timestamp_ms 양수, fingerprint format) | 422 응답 + 로깅 |
| Fingerprint format | UUID v4 또는 보조 신호 hash | 새 fingerprint 자동 생성 |
| AST 변형 결과 | round-trip 검증 (변형 후 다시 expand하면 원본 다항식과 equivalent) | 정답 인정 X, 재시도 가능 |
| 카드 difficulty_seed | 정수 1~5 | 카드 로드 거부 (콘텐츠 큐레이터 알림) |

## 5.5 데이터 보존 정책

- **익명 이벤트 로그**: 6개월 보존 후 자동 삭제 (V1 분석 기간 + 마진)
- **카드 마스터**: 영구 보존
- **CardState (localStorage)**: 사용자가 브라우저 클리어 시 자동 삭제
- **학습 데이터 서버 보존(계정 사용자, 2026-06-05 정책 확정 — 후속 구현 예정)**: SRS·스트릭·커스텀 콘텐츠 = **계정 유효 동안 무기한**. **활동 로그(activity_log)만 14일 retention**(로컬 14일 룰 미러). 보존 enforce = **서버측 일일 주기 cleanup**(`DELETE WHERE date < cutoff` — **활동일 date 버킷 기준**, 로그인 여부 무관 보장; push 단계서도 window 밖 date 거부; push-time purge 는 보조). ⚠️ 구현 중 정정(#117): retention 을 `updated_at`(서버 write시각) 기준으로 두면 14일 밖 오래된 date 가 재동기화만으로 보존 연장·heatmap 재등장하는 회귀가 있어 **활동일 `date` 버킷 기준**으로 확정. 로컬 자정↔UTC 경계는 **1일 grace**(서버 보존 window 가 로컬 14일의 상위집합 — 클라보다 덜 지우지 않음). 계정 삭제 시 전부 `ON DELETE CASCADE` 파기. 근거: `proc/plan/2026-06-05_learning-data-server-sync.md`.
- **Session (§5.3 게임플레이/분석 세션)**: 6개월 보존
  - ⚠️ 위 "Session" 은 §5.3 ERD 의 **게임플레이/분석 세션**(5문제 1세션, 이벤트 분석용) 보존 기간이다. **계정 로그인 세션과는 별개 개념**이다. 로그인 세션 TTL: **pullim 모드(정본, 2026-07-04~)** = pullim-api 소유 `.pullim.ai` 쿠키 세션(TTL·회전은 pullim-api 관할, games 미소유) / **legacy 모드(dormant)** = games `auth_sessions` opaque 토큰 **7일**(§5.2). 둘을 혼동하지 말 것 (2026-05-29 명시, 2026-07-04 SSO 개정).

### 출시 알림 신청 (V1.5 — Plan D Phase 2, **2026-05-20 정책 갱신**)

**핵심 원칙: 본 서버는 이메일 보존 0. 외부 메일 서비스에 즉시 위임.**

기존 hash-only 설계는 실제 알림 메일 발송이 불가능하다는 기능 모순(Codex 지적 #1)이 확인되어 **외부 메일 서비스 위임 모델**로 전환한다.

#### 데이터 흐름

```
클라이언트 (이메일 입력)
   │ plain email + source='billing-cta'
   ▼
/api/billing/notify  ← Zod strict 검증 (추가 필드 거부)
   │ Resend API 호출 (audience contact 등록)
   ▼
Resend (외부 메일 서비스, audience 보존)
   │ 응답 후 라우트 내 변수 폐기
   ▼
본 서버 DB·로그·메모리 잔존 0
```

#### 보안 boilerplate

- **본 서버 저장 0**: 라우트는 fetch 응답 처리 후 변수 폐기. DB·KV·파일·로그 어디에도 plain email 잔존하지 않음. 환경 무관 (production 포함) email 원문 로깅 0 — 메타데이터(`source`, `ts`, `reason`, `status`) 만 기록한다.
- **Zod strict**: `BillingNotifySignupSchema.strict()` — 정의되지 않은 필드 동봉 시 422. raw email 외 식별자 누수 방지.
- **외부 위임 응답 폐기**: Resend 의 `id` 응답은 본 서버에서 보관 X (위임 후 외부에 권한 이양).
- **외부 서비스 6개월 보존 정책**: Resend audience 측 보관 정책 따름. 사용자가 unsubscribe 시 Resend dashboard 에서 제거 — 본 서버 액션 0.
- **same-origin 가드** (2026-05-20 round 3 fix — Codex 지적 #2): 라우트는 `Origin` 또는 `Referer` 헤더가 본 사이트 origin(`NEXT_PUBLIC_SITE_ORIGIN`·`VERCEL_URL`·요청 host 중 하나) 와 일치할 때만 처리. 외부 도메인 cross-origin POST 는 403 거부. **헤더만으로는 spoof 가능하므로 다음 CSRF 토큰 가드와 함께 다층 적용**.
- **CSRF 토큰 (SameSite=Strict 쿠키)** (2026-05-21 round 10 fix — Codex 지적 #1): `Origin`·`Referer` 헤더는 비브라우저 클라이언트가 쉽게 위조 가능해 헤더 단독 가드만으로는 외부 남용 차단 효과가 약하다. 추가 가드로 `GET /api/billing/notify/csrf` 가 1회용 nonce 를 `SameSite=Strict; HttpOnly; Secure(production); Path=/api/billing/notify; Max-Age=3600` 쿠키로 발급한다. POST 요청 시 라우트가 쿠키에서 토큰 추출 → in-memory store 일치 검증 → 통과 시 1회 소비. SameSite=Strict 가 cross-origin POST 에 쿠키를 동봉하지 않으므로 curl/봇 이 헤더만 spoof 해도 nonce 부재(`missing`) 또는 형식 위조(`invalid`) 로 403. 토큰은 32 byte random hex(64 chars), TTL 1시간, 1회 소비(replay 차단). nonce store 는 모듈 스코프 Map — cold start 시 reset 되지만 폼 진입 직후 사용되는 본 use case 특성상 충분. V2 진입 시 KV 기반 stateless 토큰으로 재설계.
- **Rate limit — 3-tier NAT 친화 + Resend 일일 한도 정합** (2026-05-21 round 9·10 fix — Codex 지적 #2):
  - **tier 1 (IP 만, 분·시간)**: 30/분 + 100/시간. 학교/학원/가정 NAT 처럼 공인 IP 1개를 여러 학생이 공유하는 환경 친화. 기존 5/분 한도는 같은 NAT 안 학생이 서로를 429 로 막는 거짓 양성을 유발해 폐기.
  - **tier 2 (IP + email 해시, 시간)**: 6/시간. 같은 IP·같은 이메일 abuse 만 좁게 차단. email 해시는 normalize(lowercase + trim) 후 SHA-256(16 chars) — **rate-limit Map 의 bucket key 로만 in-memory 잔존**, DB·KV·로그·외부 위임 어디에도 저장하지 않음 (PII 0 유지). 시간 경과 시 GC.
  - **tier 3 (IP·글로벌 일일, Resend 100/일 정합 — round 10 fix #2)**:
    - **IP 일일 한도**: 20/일/IP. 단일 IP 가 Resend 무료 한도(100/일) 의 20% 이상을 단독으로 소진하지 못하도록 cap. 학교 NAT 100명 × 4명 동의 = 400/일 시나리오에서도 IP 하나당 20건만 통과 → 5개 IP 분산 시 100건 정상 처리.
    - **글로벌 일일 cap**: 80/일. Resend 무료 한도의 80% — 20% 안전 마진 확보. 도달 시 정상 사용자도 429 차단하지만 quota exhaustion 으로 알림 수집 마비되는 것보단 fail-closed 가 안전.
    - **Soft warning 임계**: 글로벌 60/일 도달 시 `console.warn('[billing/notify] daily quota soft-warning', { marker: 'daily_quota_soft_warning', dayKey, globalCount, cap, warnThreshold })` 마커 1회 — 운영 측이 quota cap 도달 전 단계에서 인지 가능.
    - day key 는 UTC `YYYY-MM-DD` 기반. 자정마다 자동 reset.
  - tier 1·tier 3 은 본문 파싱 전 적용(invalid-body 폭주 abuse 차단), tier 2 는 Zod 검증 후 적용(email 필요).
  - Resend 무료 한도(100/일) 보호 + BR-PAY3 학생 보호 (같은 이메일 abuse 대량 주입 차단).
  - 분산 환경 정밀 limit 은 V2 결제 진입 시 KV 도입과 함께 재설계 (cold start 시 카운터 reset 한계).
- **중복 등록 idempotent** (2026-05-20 round 3·5·7 fix — Codex 지적 #1): Resend 응답 중 **HTTP 409 Conflict**, 또는 4xx 응답 body 가 `\balready\s+exists\b` 정규식(대소문자 무시, 두 단어 인접 매칭) 에 일치할 때만 → 사용자 관점 success 처리. `already` / `exists` 단독 substring 매칭은 false positive(`audience does not exists` 등) 가 발생하므로 사용하지 않는다. 같은 이메일 재신청해도 "신청 실패" 가 영구 노출되지 않음. 기타 4xx(validation·auth) 는 502, 5xx 도 502, secret 미설정은 503.
- **Production 관측 신호** (2026-05-21 round 9 fix — Codex 지적 #3): Resend 위임 실패(502·503) 시 `console.error('[billing/notify] resend delegation failed', { source, ts, reason, status, marker })` 형태의 구조화 로그를 환경 무관(production 포함) 으로 남긴다. `marker` 는 `secret_missing`(503·RESEND_API_KEY 부재) 과 `external_error`(502·외부 4xx/5xx/network) 를 구분해 Vercel 로그에서 grep 가능. email 원문은 어떤 형태로도 포함되지 않는다 — PII 0 정책 보존.

### 5.7.5 외부 메일 서비스 위임 정책 (2026-05-20 합의 — Codex 지적 #1 fix)

**채택**: **Resend** (단일 메일 서비스).

#### 결정 배경

PR #91 1차 구현은 클라이언트 sha256 hash 만 받는 hash-only 모델이었으나, Codex review 가 **단방향 hash 로는 실제 출시 알림 메일 발송이 불가능** 하다는 기능 모순을 지적했다. 사용자 합의: 본 서버 PII 0 원칙은 유지하되, **외부 메일 서비스에 즉시 위임** 하여 발송 가능성을 확보한다 (옵션 C 채택).

#### 4 axis 비교 매트릭스

| 서비스 | KR 접근성 | 무료 한도 | API 단순도 | 통합 LOC 추정 | 결정 |
|---|---|---|---|---|---|
| **Resend** | 한국 IP 직접 호출 OK, 도메인·SPF·DKIM 표준 | **100/일 무료**, 도메인 1개 검증 후 즉시 | REST 1엔드포인트 (`POST /contacts` 글로벌 Contacts 모델), JSON body | ≈30 LOC + env 1~2개 | **채택** |
| Mailchimp | KR 접근 OK 단 audience 관리 UI 복잡, SDK 무거움 | 500 contacts 무료 단 발송 횟수 제약 | OAuth 또는 API key, audience id·status·tags 다단계 | ≈120 LOC | 보류 (오버엔지) |

**선택 사유** (결단력 룰 — 갈래 묻지 X, 1순위 명시):
1. **무료 한도 충분** (100/일 = V2 출시 전 알림 수집 기간 ≈3000 신청자 커버)
2. **API 단순도 최상** — fetch 직접 호출 1줄, SDK 의존성 0 (보안·번들 사이즈 보존)
3. **audience 모델 일치** — "관심자 명단" → 출시 시 단일 broadcast 발송 패턴이 본 use case 와 1:1 매칭
4. **KR 직접 호출** — 프록시·CDN 우회 없이 한국 vercel edge function 에서 직접 호출 가능

#### 데이터 흐름 (round 8 정합)

V1.5 = 단일 트랜잭션 (중복 시 +1 PATCH):

```
브라우저 → /api/billing/notify
  body: { email: string, source: 'billing-cta' }
                ↓ Zod strict 검증
        POST https://api.resend.com/contacts
          body: {
            email,
            unsubscribed: false,
            properties: { source: 'billing-launch-notify', consented_at },
            segments?: [{ id: RESEND_SEGMENT_ID }]   // env 있을 때만
          }
                ↓
        ┌─ 신규 (2xx) → 응답 폐기 → 본 서버 저장 0
        │
        └─ 중복 (409 또는 "already exists") → round 8 재구독 보장
                ↓
           PATCH https://api.resend.com/contacts/{email}
             body: { unsubscribed: false, properties: { source, consented_at } }
                ↓ 응답 폐기 → 본 서버 저장 0

본 서버 저장 0 — Resend 단일 진실 원천 (single source of truth)
```

#### Secret 관리 (round 8 — 글로벌 Contacts 모델 정합)

- 환경변수 `RESEND_API_KEY` — Vercel project secret 으로 등록. **필수** — 미설정 시 503.
- 환경변수 `RESEND_SEGMENT_ID` — 선택. 설정 시 contact 생성 페이로드에 `segments: [{ id }]` 동봉돼 즉시 해당 segment 에 추가된다. 미설정 시 `properties.source` 마커만으로 캠페인 분리.
- 환경변수 `RESEND_AUDIENCE_ID` — **deprecated** (round 8). 이전 `audiences/{id}/contacts` 경로용. 글로벌 Contacts 모델에서는 미사용. 환경에 남아 있어도 신경로는 무시.
- 환경변수 `NEXT_PUBLIC_SITE_ORIGIN` — same-origin 가드 (운영·preview 별 명시. dev 는 자동 fallback).
- 키 미설정 시 (개발·테스트·CI): 라우트는 422 가 아닌 **503 service_unavailable** 응답으로 외부 의존성 단절을 명시. 단 schema 검증은 통과 후 동작.

#### 캠페인 분리 마커 (round 8 — Codex 지적 #3 fix)

본 라우트가 생성하는 모든 contact 에 다음 `properties` 가 동봉된다:

```json
{
  "properties": {
    "source": "billing-launch-notify",
    "consented_at": "2026-05-20T07:30:00.000Z"
  }
}
```

**운영상 강제 수단**:
- 출시 broadcast 발송 시 `properties.source = 'billing-launch-notify'` 만 필터링해 발송 대상 결정.
- 다른 캠페인이 같은 Resend workspace 를 공유해도 본 source 외 contact 는 사용 금지.
- `consented_at` 은 동의 시점 기록 — 추후 GDPR-style 동의 추적·삭제 요청 응대에도 사용 가능.
- 본 마커 룰을 운영 측에서 강제 위반하면 SPEC §05.7.5 위반으로 처리 — "출시 알림 외 용도로는 사용하지 않는다" 약속은 본 마커 기준으로 검증된다.

상수 정의: `src/lib/server/billing/resend-client.ts#BILLING_SOURCE_MARKER`.

#### 응답 분기 (round 3·5·8 — 2026-05-20 갱신)

| 상황 | 외부 호출 | HTTP | 사용자 UX |
|---|---|---|---|
| Resend POST 200/201 (신규 등록) | POST `/contacts` 1회 | 200 | 성공 메시지 |
| Resend POST 409 또는 4xx + body `\balready\s+exists\b` (round 5 정규식 좁힘) | POST + **PATCH `/contacts/{email}`** (`unsubscribed: false` 재구독 보장 — round 8 #2) | 200 (idempotent + 재구독) | 성공 메시지 (재신청도 자연스럽게 처리) |
| 중복 분기에서 PATCH 자체 실패 (4xx/5xx·network 단절) | POST + PATCH 실패 | 502 | "신청 실패, 잠시 후" (거짓 success 노출 X) |
| Resend 기타 4xx (validation·auth — "already exists" 미매칭) | POST 1회 | 502 | "신청 실패, 잠시 후" |
