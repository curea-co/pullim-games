# daily_outcome 작성 규칙

**공통 변수 (모든 프로젝트 공유):**

- 사용자명 : 박승훈 (PM, 작성자)
- G1 : 대표
- G2 : 부대표
- G3 : BE 게이트키퍼
- G4 : FE 게이트키퍼

사용자명 PM의 일일 업무 보고(약속 / 진행 / 제출 3시점)를 누적·아카이빙하는 폴더의 운영 규칙. 에이전트는 사용자 발화를 받아 양식에 맞춰 **초안을 작성**하고, 사용자 검토 후 파일에 저장한다.

본 프로젝트(풀림 게임즈) 관계자: 사용자명 PM, G1, G3, G4. (G2 부대표는 본 프로젝트 미할당 — 다른 프로젝트 확장성을 위해 변수 정의는 유지)

---

## 1. 파일 구조

- 위치: `daily_outcome/YYYY-MM-DD.md` (하루 1파일)
- 시점: **09:30 약속 / 14:30 진행 / 17:30 제출** 세 섹션이 같은 파일에 순차적으로 append
- 시점 사이는 `---` 구분선
- 보고가 누락된 시점은 해당 섹션을 비워두지 않고, 시점 헤더 아래 `(미작성)` 한 줄만 남긴다

```
daily_outcome/
  CONVENTION.md           ← 이 문서 (작성 규칙)
  2026-05-13.md           ← 일일 보고
  2026-05-14.md
  ...
```

---

## 2. 양식

게이트키퍼 호칭은 양식·실제 보고 모두 `G1`/`G2`/`G3`/`G4`로 그대로 노출한다 (역할 풀어쓰기 금지 — Slack 공유 시 일관성 확보).

### 파일 헤더 (파일 생성 시 1회)

```markdown
# [사용자명 PM] Week 1 Daily Outcome — YYYY-MM-DD (요일)
```

### 시점 1 — 09:30 오늘 산출물 약속

```markdown
## 09:30 오늘 산출물 약속 — YYYY-MM-DD

1. **오늘 맡은 프로젝트**: <프로젝트명> (활성 게이트키퍼: G1 / G2 / G3 / G4 중 §5에서 ✅로 표시된 역할)
2. **오늘 만들 산출물**:
   - 산출물 A
   - 산출물 B
3. **완료 기준** (검증 가능):
   - A: <링크/파일경로/PR번호로 검증 가능한 표현>
   - B: <동일>
4. **AI에게 먼저 시킬 일** (오늘 AI 활용 지점 설계):
   - …
5. **예상 블로커**:
   - …
```

### 시점 2 — 14:30 진행 상황

```markdown
---

## 14:30 진행 상황 — YYYY-MM-DD

1. **현재 진행률**: A <%>, B <%>
2. **지금까지 나온 초안/링크**:
   - …
3. **막힌 점**:
   - …
4. **G1 또는 게이트키퍼 확인이 필요한 것**:
   - <대상자(G1 / G2 / G3 / G4 중 해당)> | <확인 필요 사항>
5. **오후에 끝낼 액션**:
   - …
```

### 시점 3 — 17:30 Daily Outcome 제출

```markdown
---

## 17:30 Daily Outcome 제출 — YYYY-MM-DD

1. **오늘 산출물 (링크)**:
   - A: <링크/파일경로/PR번호>
   - B: <동일>
2. **완료 기준 달성 여부** (09:30 항목과 1:1 매칭):
   - A: ✅ 달성 / ⚠️ 부분 달성 / ❌ 미달성 — <근거>
   - B: …
3. **내일 이어서 할 일**:
   - …
4. **배운 점 / 공유할 점**:
   - …
5. **마감 4열** (2026-05-16 이후 보고분부터 필수): 09:30 약속 산출물 각각에 대해 `오늘 약속 → 실제 산출 → PR/배포 → 검증` 4 필드로 1줄 요약. 형식 (markdown table 아님 — `|` 는 시각적 구분자, Slack 렌더링 호환):
   - A | 약속: <09:30 항목> | 산출: <실제 결과/파일/문서> | PR/배포: <PR #N + production 배포 여부> | 검증: <✅/⚠️/❌ + 근거>
   - B | …
```

## 3. 항목별 작성 기준 (정의)

### "완료 기준" — 검증 가능한 형태 강제

추상 표현 금지. 링크·파일경로·PR번호·머지여부 등 **단어 단위로 확인 가능한 단서**를 반드시 포함.

| 금지 | 권장 |
|---|---|
| "plan 작성 완료" | `proc/plan/2026-05-13_X.md` 작성 + 사용자 합의 |
| "검토 끝냄" | PR #42 머지 |
| "스펙 반영" | `proc/spec/pm-rule.md` L120-145 에 i18n 규칙 추가 |
| "기능 만들기" | `src/games/X/screen.tsx` 신규 + 라우팅 등록 |

에이전트는 추상 표현이 감지되면 **저장 전 사용자에게 구체화를 요청**한다.

### "AI에게 먼저 시킬 일" — 광의의 AI 활용 지점 설계

단순히 "AI한테 시킬 작업 목록"이 아니라, **오늘 작업 흐름에서 AI를 활용할 적절한 구간을 미리 설계**하는 항목.

포함 대상:
- 위임할 단발 작업 (예: "plan 초안 작성", "리서치 병렬 수행")
- 워크플로우 자동화 지점 (예: "사용자 인풋 → 스펙 텍스트 변환", "PR 코멘트 자동 요약")
- AI에게 맡길 의사결정 보조 (예: "디자인 안 변별력 평가")

→ "AI가 잘하는 구간을 어디로 잡을 것인가"에 대한 의도 표명.

### "G1 또는 게이트키퍼 확인이 필요한 것"

G1(대표)과의 의사결정 또는 프로젝트별 **게이트키퍼**(G2 / G3 / G4 등)와의 협의가 필요한 항목.

- 게이트키퍼 활성화 여부는 프로젝트마다 다르다. 없을 수도 있다.
- 각 프로젝트의 게이트키퍼 할당은 §5 프로젝트 등록부에서 확인.
- 게이트키퍼가 없는 프로젝트에서 이 항목이 필요하면 G1만 대상으로 표기.

기재 형식: `<대상자> | <확인 필요 사항 1줄>`

예:
- `G1 | 풀림 게임즈 콘텐츠 톤앤매너 — 학습효과 우선 가이드라인 확정`
- `G4 | 게임 모드 화면 라우팅 구조 합의`

## 4. 에이전트 동작 규칙

### 4.1 트리거 발화

사용자가 다음 부류의 발화를 하면 해당 시점 보고로 인식한다.

| 시점 | 트리거 예시 |
|---|---|
| 09:30 | "오전 보고", "Daily 시작", "오늘 산출물 약속", "09:30 보고" |
| 14:30 | "진행 보고", "오후 보고", "14:30 보고" |
| 17:30 | "Daily 마감", "제출", "17:30 보고", "오늘 완료 보고" |

명시적 시점 지정이 없으면 **현재 시각**을 기준으로 가장 가까운 시점으로 라우팅하되, 사용자에게 한 줄로 확인한다.

### 4.2 동작 순서

1. **파일 존재 확인** — `daily_outcome/YYYY-MM-DD.md`
   - 없으면 새 파일 생성 (헤더 + 시점 1)
   - 있고 해당 시점이 아직 비어있으면 append
   - 있고 해당 시점이 이미 채워져 있으면 **사용자에게 덮어쓸지 / 추가할지 / 취소할지** 확인
2. **컨텍스트 자동 수집** (사용자 추가 입력 없이 가능한 만큼)
   - 시점 1: 사용자 발화 + 최근 commits/PR + 진행 중인 plan 문서
   - 시점 2: 시점 1 내용 + 그 사이 commits/diff + 사용자 메모
   - 시점 3: 시점 2 내용 + 산출물 단서(생성/수정된 파일 경로, 머지된 PR 번호) 자동 추출
3. **양식에 맞춰 초안 채우기**
   - 모르는 항목은 빈칸이 아니라 `(확인 필요: <무엇이 비어있는지>)`로 명시
   - 추상 표현 감지 시 구체화 요청
4. **사용자에게 초안 제시** — 본 채팅창에 보여주고 검토 요청
5. **승인 시 파일에 저장**, 수정 요청 시 반영 후 다시 4번부터

### 4.3 작성 원칙 (체크리스트)

저장 직전 다음을 자가 점검한다.

- [ ] "오늘 만들 산출물"과 "완료 기준"은 1:1 대응되는가
- [ ] 모든 "완료 기준"이 검증 가능한 형태인가 (링크/파일경로/PR번호 중 하나 이상)
- [ ] 시점 3의 "완료 기준 달성 여부"가 시점 1의 완료 기준과 항목 단위로 매칭되는가
- [ ] "G1 / 게이트키퍼 확인 필요" 항목의 대상자가 §5 프로젝트 등록부에 ✅로 활성된 역할(G1 / G2 / G3 / G4)인가
- [ ] 시점 헤더의 날짜가 파일명 날짜와 일치하는가
- [ ] 일일 보고 양식 작성 내용에 표 형태가 없는가 (Slack은 markdown 표를 렌더링하지 않으므로 자유 서술·리스트 사용; 단 17:30 §5 마감 4열의 `|` 구분자는 markdown table 헤더가 없는 단순 텍스트이므로 허용)
- [ ] (2026-05-16 이후 보고분) 17:30 §5 마감 4열이 09:30 약속 산출물 각각에 대해 `약속 → 산출 → PR/배포 → 검증` 4 필드 모두 채워져 있는가

위반이 있으면 저장 전 사용자에게 보고하고 처리 방법을 묻는다.

## 5. 프로젝트 등록부

각 프로젝트의 메타 정보. 새 프로젝트가 추가되면 여기에 등록한 뒤에 daily_outcome에 사용한다.

| 프로젝트 | 설명 | G1 (대표) | G2 (부대표) | G3 (BE) | G4 (FE) |
|---|---|---|---|---|---|
| 풀림 게임즈 | 풀림 플랫폼 하위 학생용 학습+게이미피케이션 (컨셉 단계) | ✅ | 없음 | ✅ | ✅ |

작성 규칙:
- 표는 **역할 활성 여부만** 기록한다. 실제 인물 매핑은 표에서 다루지 않는다 (역할은 특정 인물과 1:1 매칭되지 않을 수 있고, 인물 변동에 표가 흔들리지 않게 하기 위함).
- 본 프로젝트에 해당 역할이 활성화되어 있으면 `✅`.
- 본 프로젝트에 해당 역할이 할당되지 않으면 `없음`.
- 역할 활성/비활성 상태가 바뀌면 이 표를 먼저 업데이트한 뒤 daily_outcome에 반영한다.
